# Review and benchmark — 29 October 2026 (0.2.2 → 0.3.0)

Scope: portability for `pi install <git source>`, a correctness review on Pi 1.4.0, and a long-session benchmark against a local Qwen3.8-27B (98,304-token window, one GPU slot).

## Which mode actually ran

| Session | Engine per compaction | Jev status | Evidence |
|---|---|---|---|
| All 47 Pi sessions in `~/.pi/agent/sessions`, 2026-09-29 → 10-24 | 17 Jev checkpoints + 1 `init`; 31 native | `missing_key` on all 17, `jevRequests: 0` | `details.metrics` of each compaction entry |
| Headless benchmark `lctest-pijev1` (earlier today, reported as "Pi + Jev 12/12") | 3/3 **native** (`fromHook: false`, no engine marker) | never reached | offline replay of each compaction: `protected_text_exceeds_budget`; pins ≈ 45.8k est. tokens vs a 32.7–39.5k budget |

The TypeSafe API has never been called from Pi on this Mac. Version 0.2.2 read the key only from the Pi process environment (`process.env.TYPESAFE_API_KEY`), and that variable wasn't set in the shell, the login environment (`launchctl`) or the rc files. In the headless benchmark, the extension stood down before key lookup, so its 12/12 measured Pi's native summarizer.

## Findings, by severity

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | High | **User requests were pinned verbatim with no size limit, and pins were carried forward forever.** When the replaced span was mostly user text (pasted files or logs, which is when compaction matters most), the checkpoint could never fit 70% of the span, so every compaction silently became native. Pins also accumulate across compactions, so a long session ends up in the same state. | **Fixed.** Verbatim pins are still used when they fit. Otherwise they're bounded: every request keeps its marker lines (NOTE, CORRECTION, must, never…), the newest requests get head/tail or full text within 2,400 est. tokens, and the rest are counted. Excerpts are labelled with their entry id for `jev_recall`. A replay of the 3 real compactions now gives Jev checkpoints of 1.8k, 3.1k and 4.4k est. tokens. |
| 2 | High | **The key came only from the environment**, so a TUI started from a shell without the export, or `pi -p` launched by a tool, always ran `missing_key`. `/jev-compact status` showed only a boolean. | **Fixed.** Optional `typesafeApiKeyFile` in `<agentDir>/pi-jev-compact.json`, read at each compaction. Status reports `jevKey: env | file | none | file_empty | file_unreadable`. |
| 3 | Medium | **Native fall-through was invisible** in `pi -p`/JSON mode (only `ctx.ui.notify`). This is why the earlier benchmark was mislabeled. | **Fixed.** A `pi-jev-compact-fallback` custom entry (not sent to the model) records the reason and key source after each native fall-through. Integration test added. |
| 4 | Medium | **An oversized Jev payload threw**, and the thrown error abandoned the whole Jev checkpoint for native compaction. JSON escaping roughly doubles code-heavy excerpts (8 × 800 chars), and the 14,000-character guard could trip with a key present. | **Fixed.** Candidate excerpts are shortened (800 → 400 → 200 characters) for Jev only; if still too large, local mode runs with `jev: "input_budget"`. |
| 5 | Medium | **Redaction gaps before sending to TypeSafe:** JSON/YAML forms (`"api_key": "…"`), AWS `AKIA…`, GitHub `ghp_…`/`github_pat_…`, Slack `xox?-…`, Google `AIza…`, JWTs. | **Fixed** with tests. It's still best effort, not DLP. |
| 6 | Medium | **This Mac was hardcoded:** the thinking filter ran only for `home-qwen`/`home-qwen-remote` + `orcarouter-qwen3.8-27b` (`loop.ts`); scripts and README had absolute paths. | **Fixed.** `stripThinkingModels` patterns default to none. This Mac keeps its previous behavior through `~/.pi/agent/pi-jev-compact.json`, written with both Home Qwen profiles. |
| 7 | Medium | Verbatim pins are still accepted up to 70% of the replaced span (a deliberate 0.1.1 choice). A checkpoint that keeps 70% frees little space and makes compaction frequent. | Not changed (design choice). Suggestion: use verbatim pins only while they're ≤ 2,400 est. tokens, and bound them otherwise. |
| 8 | Medium | `/jev-compact init` imports Pi's internal `dist/core/compaction/compaction.js` (`prepareCompaction` isn't exported from the package root, even in 1.4.0). | Works on 1.4.0; documented. It will need adjusting if Pi moves the file. Ordinary compaction doesn't depend on it. |
| 9 | Low | The integration test was stale on Pi 1.4.0: Pi no longer passes the model's `maxTokens` to native summaries. | **Fixed** (accepts both). All 4 integration suites pass on 1.4.0. |
| 10 | Low | The tests loaded the real `~/.pi/agent` config. With a key file configured, the "offline" suites would have sent data to Jev. | **Fixed.** `scripts/pi-sdk.mjs` points `PI_CODING_AGENT_DIR` at a temporary directory. |
| 11 | Low | `jev_recall` `query` is one case-insensitive substring and reports only the first hit per message. Multi-word queries ("access code vault") often return nothing. | Not changed. Suggestion: fall back to all-terms matching when the exact phrase has no hits. |
| 12 | Low | `init` uses `reserveTokens: 16384` and a 45% target regardless of the user's compaction settings. | Not changed; harmless for the 64k–98k windows tested. |
| 13 | Low | The estimator (UTF-8 bytes / 3) overstates real tokens by about 25% on code (the harness measured 3.8 chars/token), so every budget is conservative. | Documented. |
| 14 | Info | `summary` mode never produced an accepted summary from local Qwen within 20 s (VALIDATION.md). | `fast` stays the default; documented. |

### Checked and found correct

- **Tool-call/result pairing.** Pi chooses `firstKeptEntryId` and the extension never moves it. `init` rejects boundaries outside the branch. The integration suites check that every surviving `toolResult` has its call.
- **Budget vs a 98,304 window.** Pi compacts above 81,920 (98,304 − 16,384) and keeps 20,000 recent tokens. The checkpoint targets 2,400, or more only to carry a previous summary or verbatim requests, so the session resumes at roughly 25–30k.
- **`jev_recall` paging.** `id` pages the raw entry 4,000 characters at a time with an exact `nextOffset`; foreign ids are rejected. `query` pages 6 matches at a time.
- **Failure fallbacks.** No key, HTTP/network errors, timeouts (2.5 s), malformed or incoherent answers, input budget and summary failures all degrade to local or native. Only a user abort returns `cancel`.
- **Double compaction.** `billion-context` 0.1.206 still registers `compress`/`decompress`/`acp_status`, so the conflict check detects it. It is disabled in settings, as the user confirmed. `pi-hermes-memory` 0.9.11 also hooks `session_before_compact`, but only to flush memory, and returns nothing. That flush is an extra model call per compaction and per `pi -p` shutdown, and in the earlier benchmark it wrote test facts into `MEMORY.md`. The new benchmark excludes it with `--no-extensions`.
- **README vs settings.** The old README said `index.ts` was disabled. `~/.pi/agent/settings.json` has `+index.ts`, and Jev checkpoints exist from 2026-10-04 16:57 onward, so the line was stale. The new README describes no particular machine.
- **Portability.** A bare clone was installed the way Pi installs git sources: `npm install --omit=dev --omit=peer` finds no dependencies, and `pi install <path>` + `pi list` work in a sandboxed agent dir. All 32 unit tests and 4 integration suites pass from the clone. Pi rejects `git:file://` sources, so the GitHub URL itself is untested until the repository exists.

## Benchmark

`bench/lctest.py session --pi`: 24 turns × ~6,000 tokens of Python stdlib source, 12 codes planted as `# NOTE:` lines in turns 1–8, 4 changed by `# CORRECTION:` lines in turns 12–16, then one question. Each turn is a separate `pi -p` process on the same saved session, with `--no-builtin-tools --no-mcp --no-extensions --no-skills --no-context-files --no-prompt-templates`. Only the listed extensions load. Runs were strictly sequential.
