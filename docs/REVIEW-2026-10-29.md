# Review and benchmark — 29 October 2026 (0.2.2 → 0.3.0)

Scope: portability for `pi install <git source>`, a correctness review on Pi 1.4.0, and a long-session benchmark against a local Qwen3.8-27B (98,304-token window, one GPU slot).

## Which mode actually ran

| Session | Engine per compaction | Jev status | Evidence |
|---|---|---|---|
| All 47 Pi sessions in `~/.pi/agent/sessions`, 2026-09-29 → 10-24 | 17 Jev checkpoints + 1 `init`; 31 native | `missing_key` on all 17, `jevRequests: 0` | `details.metrics` of each compaction entry |
| Headless benchmark `lctest-pijev1` (earlier today, reported as "Pi + Jev 12/12") | 3/3 **native** (`fromHook: false`, no engine marker) | never reached | offline replay of each compaction: `protected_text_exceeds_budget`; pins ≈ 45.8k est. tokens vs a 32.7–39.5k budget |

The TypeSafe API has never been called from Pi on this Mac. Version 0.2.2 read the key only from the Pi process environment (`process.env.TYPESAFE_API_KEY`), and that variable wasn't set in the shell, the login environment (`launchctl`) or the rc files. In the headless benchmark, the extension stood down before key lookup, so its 12/12 measured Pi's native summarizer.

## Findings, by severity

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | High | **User requests were pinned verbatim with no size limit, and pins were carried forward forever.** When the replaced span was mostly user text (pasted files or logs, which is when compaction matters most), the checkpoint could never fit 70% of the span, so every compaction silently became native. Pins also accumulate across compactions, so a long session ends up in the same state. | **Fixed.** Verbatim pins are still used when they fit. Otherwise they're bounded: every request keeps its marker lines (NOTE, CORRECTION, must, never…), the newest requests get head/tail or full text within 2,400 est. tokens, and the rest are counted. Excerpts are labelled with their entry id for `jev_recall`. A replay of the 3 real compactions now gives Jev checkpoints of 1.8k, 3.1k and 4.4k est. tokens. A follow-up fix (after the benchmark) ranks marked lines before head/tail lines, so the larger version of a pin can't drop marker lines the minimal one kept when the first and last lines are long (regression test added). |
| 2 | High | **The key came only from the environment**, so a TUI started from a shell without the export, or `pi -p` launched by a tool, always ran `missing_key`. `/jev-compact status` showed only a boolean. | **Fixed.** Key file read at each compaction: `~/.config/jev/typesafe.key` by default, or `typesafeApiKeyFile` in `<agentDir>/pi-jev-compact.json`; `TYPESAFE_API_KEY` still wins. Status reports `jevKey: env | file | none | file_empty | file_unreadable`. |
| 3 | Medium | **Native fall-through was invisible** in `pi -p`/JSON mode (only `ctx.ui.notify`). This is why the earlier benchmark was mislabeled. | **Fixed.** A `pi-jev-compact-fallback` custom entry (not sent to the model) records the reason and key source after each native fall-through. Integration test added. |
| 4 | Medium | **An oversized Jev payload threw**, and the thrown error abandoned the whole Jev checkpoint for native compaction. JSON escaping roughly doubles code-heavy excerpts (8 × 800 chars), and the 14,000-character guard could trip with a key present. | **Fixed.** Candidate excerpts are shortened (800 → 400 → 200 characters) for Jev only; if still too large, local mode runs with `jev: "input_budget"`. |
| 5 | Medium | **Redaction gaps before sending to TypeSafe:** JSON/YAML forms (`"api_key": "…"`), AWS `AKIA…`, GitHub `ghp_…`/`github_pat_…`, Slack `xox?-…`, Google `AIza…`, JWTs. | **Fixed** with tests. It's still best effort, not DLP. |
| 6 | Medium | **This Mac was hardcoded:** the thinking filter ran only for `home-qwen`/`home-qwen-remote` + `orcarouter-qwen3.8-27b` (`loop.ts`); scripts and README had absolute paths. | **Fixed.** `stripThinkingModels` patterns default to none. This Mac keeps its previous behavior through `~/.pi/agent/pi-jev-compact.json`, written with both Home Qwen profiles. |
| 7 | Medium | Verbatim pins are still accepted up to 70% of the replaced span (a deliberate 0.1.1 choice). A checkpoint that keeps 70% frees little space and makes compaction frequent. | Not changed (design choice). Suggestion: use verbatim pins only while they're ≤ 2,400 est. tokens, and bound them otherwise. |
| 8 | Medium | `/jev-compact init` imports Pi's internal `dist/core/compaction/compaction.js` (`prepareCompaction` isn't exported from the package root, even in 1.4.0). | Works on 1.4.0; documented. It will need adjusting if Pi moves the file. Ordinary compaction doesn't depend on it. |
| 9 | Low | The integration test was stale on Pi 1.4.0: Pi no longer passes the model's `maxTokens` to native summaries. | **Fixed** (accepts both). All 4 integration suites pass on 1.4.0. |
| 10 | Low | The tests loaded the real `~/.pi/agent` config. With a key file configured, the "offline" suites would have sent data to Jev. | **Fixed.** `scripts/pi-sdk.mjs` points `PI_CODING_AGENT_DIR` at a temporary directory. |
| 11 | Medium | **`jev_recall` search found mostly itself.** `query` was one exact substring, and tool calls are rendered into the searched text. In run B both of the model's multi-word queries matched nothing except the model's own `jev_recall({...})` call. The 12/12 there came from the checkpoint alone. | **Fixed after the benchmark** (runs B and C use the old search). The tool's own calls are excluded, and an exact phrase with no hits falls back to messages containing every query term. |

### Checked and found correct

- **Tool-call/result pairing.** Pi chooses `firstKeptEntryId` and the extension never moves it. `init` rejects boundaries outside the branch. The integration suites check that every surviving `toolResult` has its call.
- **Budget vs a 98,304 window.** Pi compacts above 81,920 (98,304 − 16,384) and keeps 20,000 recent tokens. The checkpoint targets 2,400, or more only to carry a previous summary or verbatim requests, so the session resumes at roughly 25–30k.
- **`jev_recall` paging.** `id` pages the raw entry 4,000 characters at a time with an exact `nextOffset`; foreign ids are rejected. `query` pages 6 matches at a time.
- **Failure fallbacks.** No key, HTTP/network errors, timeouts (2.5 s), malformed or incoherent answers, input budget and summary failures all degrade to local or native. Only a user abort returns `cancel`.
- **Double compaction.** `billion-context` 0.1.206 still registers `compress`/`decompress`/`acp_status`, so the conflict check detects it. It is disabled in settings, as the user confirmed. `pi-hermes-memory` 0.9.11 also hooks `session_before_compact`, but only to flush memory, and returns nothing. That flush is an extra model call per compaction and per `pi -p` shutdown, and in the earlier benchmark it wrote test facts into `MEMORY.md`. The new benchmark excludes it with `--no-extensions`.
- **README vs settings.** The old README said `index.ts` was disabled. `~/.pi/agent/settings.json` has `+index.ts`, and Jev checkpoints exist from 2026-10-04 16:57 onward, so the line was stale. The new README describes no particular machine.
- **Portability.** A bare clone was installed the way Pi installs git sources: `npm install --omit=dev --omit=peer` finds no dependencies, and `pi install <path>` + `pi list` work in a sandboxed agent dir. All 32 unit tests and 4 integration suites pass from the clone. After publishing, `pi install git:github.com/maccagnit/pi-jev-compact@v0.3.0` into a sandboxed agent dir cloned the tag, registered the package, and the unit tests passed from that clone.

## Benchmark

`bench/lctest.py session --pi`: 24 turns × ~6,000 tokens of Python stdlib source, 12 codes planted as `# NOTE:` lines in turns 1–8, 4 changed by `# CORRECTION:` lines in turns 12–16, then one question. Each turn is a separate `pi -p` process on the same saved session, with `--no-builtin-tools --no-mcp --no-extensions --no-skills --no-context-files --no-prompt-templates`. Only the listed extensions load. Runs were strictly sequential.

| Run | Extensions | Compactions as recorded in the session | Model work spent on compaction | Codes | Corrections | Stale | Slowest turn | Sum of 24 turns |
|---|---|---|---|---|---|---|---|---|
| A — Jev off | `loop-guard.ts` | 2 × native (`fromHook: false`) | 2 summary calls: 62,054 + 66,529 tokens | 12/12 | 4/4 | 0 | 122 s (compaction turn) | 432 s |
| B — Jev, local mode | `index.ts`, `loop-guard.ts`; no key | 2 × Jev, `jev: missing_key`, pins `bounded`, 2,170 / 2,644 est. tokens | none | 12/12 | 4/4 | 0 | 26 s | 238 s |
| C — Jev, API mode | same; key from `~/.config/jev/typesafe.key` | 2 × Jev, `jev: ok`, 1 request each (1,942 / 2,052 Jev input tokens, 312 / 299 ms), 2,165 / 2,669 est. tokens | none (Jev only) | 12/12 | 4/4 | 0 | 26.5 s | 239 s |
| *Reference: earlier "Pi + Jev" run, 0.2.2 + pi-hermes-memory* | *installed set* | *3 × native (Jev declined: `protected_text_exceeds_budget`)* | *3 summary calls + memory flushes* | *12/12* | *4/4* | *0* | *146 s* | *651 s* |

What this shows:

- **Recall doesn't separate the configurations.** All three keep every code and correction. Pi's native summarizer is strong on this task, and the 0.3.0 pins keep the marked lines.
- **Cost and latency do.** Native compaction stalls the turn that triggers it by about 80–110 s and spends about 128k tokens of local-GPU summarization per session. The Jev checkpoint takes milliseconds and no generation, so the whole session ran about 45% faster (238 s vs 432 s of turn time).
- **API vs local made no difference here.** Jev classified all 8 candidate excerpts per compaction as kept (no ARCHIVE ≥ 0.9). The candidates are short `ACK part n` replies, so there was nothing to discard. A real coding session with large tool outputs is where Jev's choices would matter; this benchmark doesn't exercise that.
- **`jev_recall` contributed nothing in B and C**: both of the model's queries matched only its own call (finding 11, fixed afterwards). Replaying the same queries against run C's session with the fixed search returns the original `# NOTE` and `# CORRECTION` lines.
- Single run per configuration, temperature 0. Turn times exclude the final question turn. Runs B and C used the code as committed in `bd3f760`, with the key-file default from `44a719c` added before C. The later `jev_recall` fix wasn't benchmarked.

Caveat: the planted facts are lines that begin with `NOTE`/`CORRECTION`, which are exactly the lines the bounded pins prioritize. That makes the benchmark favorable to 0.3.0's pin policy. Facts buried in unmarked prose would rely on head/tail lines, `jev_recall` or the recent tail.

## Benchmark 2: a real coding session (Progetto-AI-Trading)

`bench/codesession.py`: a shallow clone of the user's Progetto-AI-Trading (`dev`) in a temp folder, `pi -p` with file tools only (`read, grep, find, ls, edit, write` + `jev_recall`; no `bash`, so nothing can execute), 13 work turns, then the clone is **deleted** and the model is quizzed. The work turns:

- 4 exploration turns: read config, risk, exits, strategy and regime code and answer questions.
- 1 turn of user rules: never touch `live/`, new behaviour default-OFF, the next step is a walk-forward.
- 4 edit turns: add a cooldown setting and a helper (the model chooses the names), a rename of a function that doesn't exist (a planted failure), and a design note.
- 4 more reading turns (backtest runner, live orchestrator, reconciliation, walk-forward and Monte Carlo) to push the edits out of the recent tail.

The answers live in tool results and in the model's own edits, not in user text. The original repository was verified unchanged after each run.

| | Pi native | Jev 0.3.0 (API mode) |
|---|---|---|
| Compactions | 1 native summary (8,076 chars; 16,344 model tokens) | 1 Jev checkpoint (1,072 est. tokens; `jev: ok`; 3 of 8 excerpts archived, all redundant) |
| Edits compacted before the quiz | yes | yes |
| Own edits recalled (name, file, default, helper, doc file) | 6/6 | 6/6 (plus the extra flag it added) |
| Planted failure recalled ("rename failed: function doesn't exist") | yes | yes |
| Explored facts (11 values/function names, scored against the code) | 11/11 | 11/11 |
| User rules / decision / next step | 3/3 | 3/3 |
| Free summary (12 rubric terms) | 12/12 | 12/12 |
| How it answered the quiz | from the summary, 0 tool calls | 13 `jev_recall` lookups into the raw history |
| Compaction turn | 95 s | 40 s |
| Total time, 16 turns | 359 s | 312 s |

Scores for own edits were checked by hand against each clone's diff (the script's automatic key misread the defaults). Caveats:

- n = 1 per arm, and only one compaction per run: Pi's read tool truncates large files, so the context grew less than planned.
- The quiz said "you may use any session-history tool you have". Without that hint, the Jev arm depends on the model deciding on its own to call `jev_recall` (the checkpoint header tells it to).
- Excerpts sent to TypeSafe in the Jev arm: at most 8 × 800 characters of this repository's code and replies, after credential redaction. The repo's tracked files were scanned beforehand and contain no secrets.

Verdict: on this session the two systems are **equally accurate** and Jev is **faster** (the compaction turn took less than half the time, with no summary generation). They remember differently. Pi's summary carries the state forward in prose. Jev keeps a small checkpoint and relies on the model looking things up in the untouched history, which here it did reliably.
